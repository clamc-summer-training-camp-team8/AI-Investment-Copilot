# 0001. 以模块所有权划分单体后端，暂不拆微服务

- 状态：已接受
- 日期：2026-08-08
- 决策人：架构负责人
- 影响模块：`app/*`、`tests/*`、CI

## 背景

团队要按功能模块分工协作，不同成员负责不同模块。需要一种能让多人并行开发、又不会互相踩踏的代码组织方式。

约束：

- MVP 容量假设为 50 名用户、30 家公司、100 条逻辑、1 万份历史资料（PRD 12.2），不存在性能上的拆分压力。
- PRD 8.3 已经明确「业务 API 可与业务服务合并」「规则与计算模块 MVP 可嵌入业务服务」「AI 编排模块 MVP 可作为单体模块」。
- 团队规模小，MVP 阶段验收目标是完整闭环（PRD 13.1），不是系统弹性。

## 备选方案

**A. 按技术类型平铺（controllers / services / models）**

优点：Python Web 项目常见，上手快。
代价：所有人都在同一批目录里改文件，冲突集中；模块所有权无法落到目录，CODEOWNERS 形同虚设；业务边界不可见，容易出现「service 里啥都有」。

**B. 单体，按业务模块划分目录与所有权**

优点：模块边界与 PRD 分层一一对应；CODEOWNERS 可按目录精确生效；冲突面小；将来要拆服务时按模块整体切走。
代价：需要额外工具（import-linter）来防止模块间偷偷互相依赖，否则「模块化」只是目录形式。

**C. 一开始就拆微服务**

优点：物理隔离，所有权最彻底。
代价：以当前规模，会把模块边界问题升级为分布式一致性、部署、联调问题；MVP 闭环要求跨模块事务（确认证据同时写版本与审计），分布式实现代价高且没有收益。

## 决策

选 B。单体后端，按业务模块划分目录并绑定负责人，用 import-linter 在 CI 中强制分层依赖。

## 代价

- 需要维护 `.importlinter` 配置，新增模块时要同步更新，否则新模块处于无约束状态。
- 单体共享一个部署单元，某模块的严重缺陷会影响整个服务。通过测试分层和配置开关缓解，不通过物理隔离解决。
- 模块边界靠工具而非进程保证，工具被绕过（运行时 import）时会失效，因此评审时需人工关注这类写法。

## 影响

- `app/` 下每个模块建 README，写明职责、边界、对外接口。
- 根目录新增 `.importlinter`，`make lint-arch` 与 CI 执行。
- `.github/CODEOWNERS` 按模块目录配置负责人。

## 回退条件

出现以下任一情况，重新评估拆分：

- 某模块的部署节奏与其余部分明显冲突（例如 AI 模块需要独立扩容或独立发布窗口）。
- 用户量或资料量超出 MVP 容量假设一个数量级。
- import-linter 例外条目持续增长，说明边界设计本身有问题——此时应先修边界，而不是直接拆服务。
