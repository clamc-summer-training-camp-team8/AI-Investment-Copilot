# 0004. 跨模块协作以契约文件为先

- 状态：已接受
- 日期：2026-08-08
- 决策人：架构负责人、各模块负责人
- 影响模块：`contracts/`、`app/ai`、`app/api`、`web`、`analytics`、`tests/contract`

## 背景

模块由不同成员负责，最容易卡住的不是各自的实现，而是接口：前端等后端接口、服务层等 AI 输出格式、离线分析等指标口径。如果接口只存在于某一方的代码里，另一方只能等对方写完才能开工。

数据分析说明书 T11 已经定义了六类数据契约（DocumentIngest / ThesisMetricMap / EventImpact / MetricValidation / OutcomeLabel / EvaluationRun），PRD 10.1~10.4 定义了四类 AI 任务的输入输出。这些契约本来就是需求的一部分，应当先落成文件。

## 备选方案

**A. 接口以实现代码为准，消费方读源码对齐**

优点：没有额外维护成本。
代价：消费方必须等生产方实现完成；接口变更无法被 CI 感知，破坏性改动在联调时才暴露。

**B. 契约文件（JSON Schema / OpenAPI）作为单一事实来源，双方各自对着契约开发**

优点：双方可并行；契约变更走 PR 并需双方 approve，破坏性改动在评审时暴露；契约测试可以在 CI 中校验实现与契约一致。
代价：需要维护契约文件与实现的同步，存在双写；契约本身也需要版本管理。

## 决策

选 B。

- `contracts/ai/` 放 AI 任务的输入输出 JSON Schema，与 `app/ai/prompts` 的版本号对应。
- `contracts/api/` 放 OpenAPI 片段与统一错误码，`web/` 依此开发，不读后端内部结构。
- `contracts/events/` 放异步任务载荷与内部事件定义。
- `tests/contract/` 校验实现输出与契约一致，CI 必跑。
- 契约文件的 PR 需 1 个 approve（CODEOWNERS 配置保证），并在 PR 里 @ 上受影响的消费方。原文要求生产方与消费方双 approve，ADR-0005 收窄为 1 个以降低等待成本；`contracts/` 仍在强制评审范围内。

契约演进规则：向后兼容的新增字段可直接改；删除字段、改字段类型、改枚举取值视为破坏性变更，需新版本号并保留旧版本至消费方迁移完成。枚举取值受 `app/core/enums.py` 约束，改动同时影响历史数据可复算性，需额外说明迁移方案。

## 代价

- 契约与实现双写，存在不一致风险。靠 `tests/contract/` 兜底，但契约测试本身写得不全时仍会漏。
- 早期契约会频繁变动，可能产生「改契约比改代码还慢」的感觉。接受这个初期成本，换取模块可并行。

## 影响

- `contracts/` 建立目录与 README，各子目录说明所属与消费方。
- CODEOWNERS 中 `contracts/` 配置多个负责人。
- 新增跨模块交互时，PR 检查清单要求先有契约文件。

## 回退条件

若某类契约长期只有一个生产方和一个消费方且都在后端内部，可以退化为共享的 Pydantic 模型放在 `app/schemas`，不必维护独立 Schema 文件。跨语言边界（前后端、离线在线）不适用这个退化。
