# 0006. 公开披露数据纳入版本控制

- 状态：已接受
- 日期：2026-08-11
- 决策人：项目负责人、数据分析负责人
- 影响模块：`.gitignore`、`real_data/`、`tests/`、`analytics/`、协作规范

## 背景

上一轮定的规则是「真实投研资料不进仓库」，`.gitignore` 里写着 `/real_data/`。
这条规则在当时是对的：那时 `real_data/` 里放的是人工摘录改写的研报摘要，来源与
授权状态都不清晰。

扩到三个行业九家公司之后，`real_data/` 的内容性质变了。现在里面是：

| 文件 | 内容 | 来源 |
| --- | --- | --- |
| `raw/announcements.json` | 3784 条公告清单（标题、披露时间、公告编号、原文链接） | 巨潮资讯网公开检索接口 |
| `raw/financials.json` | 九家公司的分季度营收与成本 | 交易所定期报告，经东财 F10 整理 |
| `raw/quotes.json` | 九家公司与三个基准指数的前复权日收盘价 | 公开行情接口 |
| `dataset/*.csv,json` | 上述数据的派生标注与投资逻辑 | 由管道确定性生成 |

全部是依法强制公开披露的信息，任何人都能从原始渠道免费取得，不含授权限制、
不含个人信息、不含未公开材料。

规则不改会带来实际成本：`real_data/` 不进版本控制，意味着每个团队成员要各自跑
一遍采集才能看到数字。而采集是有随机性的——行情源会限流、公告接口翻页边界会
返回重复项、上游随时可能调整数据。结果是不同人手里的「同一份」数据不完全一致，
评审时无法判断数字差异是代码改动引起的还是数据版本不同引起的。这与
`analytics/README.md` 要求的「口径可复算」直接冲突。

## 备选方案

**A. 保持 `real_data/` 完全不进版本控制**

优点：合规边界最简单，一句话说得清。
代价：数据不可复算。每个人的采集结果都略有不同，评审时无法区分「代码变了」
与「数据变了」。而这批数据本来就是公开的，保护它没有对应的风险要防。

**B. 只提交派生数据集，不提交原始采集结果**

优点：仓库更小。
代价：派生数据集是原始数据加规则算出来的，没有原始数据就无法验证派生是否正确。
真出现争议时，「你重跑一遍采集看看」不是一个可复算的答案。

**C. 全部提交，包括分片缓存与备份**

代价：分片缓存是中间产物，可以由 `announcements.json` 完全复原，提交它只会在
多人各自跑采集时制造无意义的冲突。

## 决策

采用 **B 与 C 之间的方案**：提交原始采集结果与派生数据集，排除中间产物与备份。

`.gitignore` 保留三条排除：

```
/real_data/raw/announcements/   # 采集分片缓存，可由 announcements.json 复原
/real_data/raw/quotes/          # 同上
/real_data/**/*.bak.json        # 上一轮范围的备份快照
```

`/uploads/` 继续排除，且这一条不放开：用户上传文件的来源不可控，可能含未公开
材料或个人信息，与「交易所强制披露信息」是完全不同的性质。

## 边界：什么仍然不能进仓库

放开的是「公开披露数据」这一类，不是「真实数据」这个大类。以下仍然禁止提交：

1. **非公开信息**：未披露的业绩、内部沟通记录、尚未公告的交易信息。
2. **带授权限制的内容**：付费数据库的导出、券商研报原文、第三方付费数据。
   注意公告清单里的 `url` 指向巨潮的公开原文，可以提交；但把研报 PDF 下载下来
   放进仓库不行。
3. **个人信息**：任何自然人的身份、联系方式、持仓。
4. **用户上传的原始文件**：见 `/uploads/`。
5. **凭证与密钥**：`.env`、token，这条从来没松过。

判断标准一句话：**能否从官方公开渠道免费取得，且取得时不需要接受任何使用限制。**
拿不准就当作不能提交，在 PR 里问。

## 后果

**好的一面**

- 数据可复算。任何人 clone 之后跑 `PYTHONPATH=. python scripts/run_industry_case.py`
  就能得到与报告完全相同的数字，不需要联网采集。
- 集成测试不再必然 skip。`tests/integration/test_industry_case_loop.py` 原来
  在 CI 里一定跳过（因为数据不在版本控制内），现在能真正跑起来，验收报告里的
  样本量断言变成了持续生效的检查。
- 数据变化在 diff 里可见。上游修订了某条公告的披露时间，评审时能直接看到。

**代价**

- 仓库体积增加约 1.5 MB（公告清单占大部分）。可以接受。
- 数据更新会产生大 diff。约定：数据更新单独提交，不与代码改动混在一个提交里，
  否则评审时看不清代码改了什么。
- 需要在文档里反复说明「公开披露数据可提交」不等于「真实数据都可提交」。
  这就是本 ADR 存在的原因。

## 影响的既有文档

以下文档里「真实投研资料/真实公司财务数据不进版本控制」的表述需要按本 ADR 修正：

- `tests/conftest.py`
- `CONTRIBUTING.md`
- `app/ingest/README.md`
- `real_data/README.md`
- `docs/validation/真实案例闭环验证.md`
- `docs/data/MVP验收报告-储能行业.md`
- 各采集脚本的模块文档

修正方式是加一句「本文写作时的表述已不适用」并指回本 ADR，而不是改写历史结论。
上一轮的报告记录的是当时的事实，直接改会让它与当时的提交记录不一致。
