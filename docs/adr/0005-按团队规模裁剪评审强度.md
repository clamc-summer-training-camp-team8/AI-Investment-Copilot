# 0005. 按团队规模裁剪评审强度

- 状态：已接受
- 日期：2026-08-08
- 决策人：项目负责人、架构负责人
- 影响模块：`.github/`、协作规范、`CONTRIBUTING.md`、`Makefile`

## 背景

ADR-0003 确立主干开发 + 模块负责人评审后，落地的流程对 2-3 人团队偏重：

- PR 模板 21 个勾选框，其中 8 个是 CI 已经在查的项（分层依赖、`make check`、迁移 head、README 齐备、`.env` 泄露）。
- `CODEOWNERS` 给 16 个路径配了负责人，任何 PR 都至少要等一个人 approve。
- 4 类改动要求先写 ADR 才能合并。
- 提交信息强制 `Refs:` 编号，分支命名与 400 行上限写成要求。

实测 `make check` 全跑 1.05 秒。也就是说流程时间几乎全部花在等人和填表上，不在等机器。

勾选框与实际检查重复还有个副作用：20 个框会被整列勾完，于是真正需要人判断的那几条也被淹没。这不是纪律问题，是清单设计问题。

## 备选方案

**A. 保持 ADR-0003 的完整评审矩阵**

优点：每个改动都有第二双眼睛；模块所有权边界清晰。
代价：2-3 人团队里，每个 PR 引入数小时到一天的等待，且评审内容大量与 CI 重复。人少时"第二双眼睛"经常就是唯一的另一个人，他同时也在等你评审他的 PR。

**B. 全部放开：不要求 PR，直接推 `main`**

优点：零流程开销。
代价：放弃 ADR-0003 的目标本身——避免各自维护互不兼容的版本。且 `contracts/` 与 `alembic/versions/` 改错时无人察觉，这两类的返工成本远高于评审成本。

**C. 按后果不可逆性分级：默认自合，四类路径强制评审**

优点：绝大多数改动零等待；不可逆改动仍有把关。机器门禁全保留，成本 1 秒。
代价：普通模块的改动没有第二双眼睛，产品红线类问题可能进主干后才被发现。需要作者自律。

## 决策

选 C。

具体规则：

1. **分支保护**：`Require approvals = 0` + `Require review from Code Owners` + 三个 CI check 必过。普通改动 CI 绿即可自行 squash merge，开 auto-merge 自动化这一步。
2. **`CODEOWNERS` 收窄到四类不可逆路径**：`contracts/`（代价由消费方承担）、`alembic/versions/`（线上数据改错无法靠回滚代码挽回）、`.importlinter`（放宽约束等于放宽全仓边界）、`docs/product|data/`（验收口径变化）。其余路径无 owner。
3. **PR 模板从 21 个勾选框改为 5 个问题**，只留机器查不了的产品红线项，且只要求回答有风险的那几条。
4. **降为建议**：分支命名、提交信息格式、`Refs:` 编号、PR 行数上限、3 天合回。不作为驳回理由。
5. **ADR 不阻塞合并**：先合代码，一周内补记录。
6. **补 pre-commit hook**（`make hooks`，走 `core.hooksPath` 使其受版本控制），允许 `--no-verify` 跳过。把「CI 红了再推一次」的往返前移到本地 1 秒。

保留不变的部分：`main` 受保护且必须走 PR、四层机器门禁、六条产品红线、迁移单 head 与可回退。

## 代价

明确接受以下坏处：

- **普通模块改动没有第二双眼睛。** 产品红线类问题可能进主干后才发现，届时需要 revert。判断依据是：这类问题的发现成本低（`main` 始终可运行、有测试），而每个 PR 的等待成本是确定发生的。
- **代码风格与提交历史会不如强制要求时整齐。** 接受，因为不整齐的后果只是观感。
- **作者自审的有效性依赖自律。** PR 模板从 21 项减到 5 项正是为此：短清单才会被真读。
- **`CODEOWNERS` 占位符未替换时，四类不可逆路径实际无人把关。** 已在协作规范第 8 节标注为接入远端的第一件事。

## 影响

- `.github/CODEOWNERS` 从 16 个路径收窄到 5 个条目。
- `.github/pull_request_template.md` 从 21 个勾选框改为 5 个问题。
- `docs/collaboration/README.md` 新增第 0 节（成本预算）与第 10 节（何时把约束加回来），重写第 1-5、7-9 节。
- `CONTRIBUTING.md`、根 `README.md` 协作段同步。
- 新增 `scripts/hooks/pre-commit` 与 `make hooks`。
- `tests/contract/test_repo_structure.py` 的 `test_codeowners_覆盖每个模块` 替换为 `test_不可逆路径仍要求评审`——守门对象从"每个模块都有负责人"变为"四类不可逆路径不被误删"。

不影响：代码结构、分层依赖规则、产品红线、CI 的检查项。

## 回退条件

出现以下任一信号时，加回对应约束（协作规范第 10 节有对照表）：

- 团队规模到 5-6 人 → `CODEOWNERS` 补模块负责人条目。
- `main` 上出现过一次需要 revert 的产品红线问题 → `Require approvals` 提到 1。
- 同一模块反复被不熟悉它的人改坏 → 该模块单独加 code owner。
- 合并冲突开始频繁 → 引入 merge queue，而不是限制分支数或延长评审。

反向的判断标准：不因为"感觉不规范"而加约束。每条约束都要能说出不遵守会发生什么。

本 ADR 调整 ADR-0003 的落地强度，不推翻其结论（主干开发 + 受保护 `main` 仍然成立）。
