# 0003. 主干开发 + 模块负责人评审的协作模型

- 状态：已接受
- 日期：2026-08-08
- 决策人：项目负责人、架构负责人
- 影响模块：全仓、CI、分支保护配置

## 背景

团队要按模块分工，同时必须避免出现「各自长期维护互不兼容的版本」。需要确定分支模型和评审机制。

## 备选方案

**A. Git Flow（长期 develop + release + feature 大分支）**

优点：发布节奏清晰，适合有明确版本窗口的产品。
代价：feature 分支生命周期长，模块间集成推迟到合并时才发生；MVP 阶段各模块接口还在变，晚集成会把小分歧攒成大冲突。这正是要避免的失败模式。

**B. 主干开发（trunk-based）：短分支 + PR 合入受保护 main**

优点：集成频繁，接口变化当天暴露；`main` 始终可运行，能随时演示；配合 CODEOWNERS 可精确落实模块所有权。
代价：要求 CI 快且稳，否则合并会排队；未完成能力必须靠配置开关藏在主干里，需要额外纪律。

**C. 每人一个 fork**

优点：权限隔离彻底。
代价：小团队里徒增同步成本，且与「统一主干集成」的目标相反。

## 决策

选 B。

- `main` 为唯一集成分支，受保护，禁止直接推送，禁止 force push。
- 特性分支短生命周期，命名 `<type>/<module>-<slug>`，建议 3 天内合回主干。
- PR 必须通过 CI，并获得对应模块负责人 approve。跨模块或改动 `contracts/`、`docs/architecture/` 需相关双方 approve。
- 合并方式统一 squash merge，保持主干线性历史，便于二分定位。
- 未完成能力用 `app/core/config.py` 中的配置开关控制，默认关闭，允许半成品进主干。

评审规范细则见 [`../collaboration/README.md`](../collaboration/README.md)。

## 代价

- 单人开发时 PR 评审会成为等待瓶颈。缓解方式：紧急修复允许事后评审，但必须在 24 小时内补 approve 记录。
- 配置开关会积累。约定每个开关在引入时登记预期移除时间，能力稳定后清理，否则分支逻辑会长期留在代码里。
- squash merge 丢失分支内的细粒度提交历史。接受这个代价，换取可读的主干历史。

## 影响

- `.github/CODEOWNERS`、`.github/pull_request_template.md`、`.github/workflows/ci.yml` 落地。
- 远端仓库需配置分支保护：要求 PR、要求 CI 通过、要求 code owner 评审、禁止 force push。配置步骤见协作规范。

## 回退条件

若 CI 时长使 PR 平均等待超过半天，先优化 CI（分层跑测试、缓存依赖），而不是放宽分支保护。若团队规模增长到单一 `main` 出现频繁合并冲突，再考虑引入 merge queue。
