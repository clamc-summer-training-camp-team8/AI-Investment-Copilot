# `phase2-integrated` 合入 `main` 与上线评估

> 评估日期：2026-08-31  
> 注：远端实际分支名是 `phase2-integrated`，不是 `phase2-integred`。

## 1. 结论

**技术上可以合并，并且在正式对外上线前有必要合并；当前不应直接把尚未提交的工作树推到
`main`。**

`origin/main` 是 `origin/phase2-integrated` 的直接祖先。2026-08-31 实测两者提交计数为
`0 / 90`：`main` 没有仅属于自己的提交，`phase2-integrated` 领先 90 个提交。因此以当前远端提交
为基准可以 fast-forward，不存在历史合并冲突。

但当前共享环境还包含登录、账号、量化产品化和部署脚本等尚未整理为远端提交的工作树变更。
若此时只把远端 `phase2-integrated` 快进到 `main`，`main` 并不等于实际运行版本；若把整个脏工作树
直接提交到 `main`，又会失去评审边界。这两种做法都不适合作为交付基线。

## 2. 为什么正式上线应基于 `main`

`phase2-integrated` 适合作为多成员功能集成和验收分支；`main` 应代表可发布、可回滚、可追溯的
产品基线。正式上线基于 `main` 有四个直接收益：

1. 团队对“线上是什么版本”只有一个答案；
2. CI、版本标签、发布审批和回滚都绑定同一条受保护分支；
3. 后续 Phase 3 不需要长期从临时集成分支继续分叉；
4. 交付文档、数据库 migration head、容器镜像标签和 Git commit 能形成一一对应关系。

这不是要求日常开发直接提交 `main`。个人功能仍在功能分支开发，先合入集成分支联调，达到发布
门禁后再通过 PR 晋升到 `main`。

## 3. 推荐晋升流程

### 第一步：冻结发布候选

1. 把当前不同主题的工作树拆成可审查提交，至少区分数据治理、量化产品化、产品内登录/部署；
2. 提交到 `phase2-integrated` 或由对应功能分支 PR 合入；
3. 确认 `git status` 干净，远端分支包含共享环境实际运行的所有代码；
4. 以提交 SHA 重建镜像，不使用“提交 SHA + 未提交文件”的混合版本。

### 第二步：通过发布门禁

- Ruff、mypy、分层依赖、OpenAPI/Schema/数据资产契约通过；
- 单元、契约、PostgreSQL 集成测试和前端生产构建通过；
- 在共享环境完成登录、首次改密、动态业务链、Graph RAG、量化实验和审计抽查；
- 发布前备份与恢复点可用，数据库只有一个 Alembic head；
- 域名、公开 HTTPS、80/443、SSH 收敛和管理员交接达到交付要求。

### 第三步：PR 合入 `main`

由于 `main` 当前是祖先，可以选择 fast-forward；团队协作中更推荐保留一次有说明的 PR merge，记录
发布范围、验收证据和审批人。若在准备期间 `main` 出现新提交，则重新合并并完整复跑门禁，不再假定
可以 fast-forward。

合并后创建不可变标签，例如：

```text
v0.2.0-phase2
```

容器镜像使用 `版本标签-完整或短 SHA`，上线部署只接受已存在于 `origin/main` 的提交。禁止重新覆盖
同名标签或镜像。

### 第四步：从 `main` 重发并回归

1. 对当前共享数据库再做一份成套备份；
2. 从 `main` 标签构建并发布，不因代码相同而沿用工作树镜像；
3. 验证迁移版本、7 个服务、登录/改密、Graph RAG 和关键动态页面；
4. 观察一个稳定窗口后，把 `phase2-integrated` 保留为下一轮集成分支或归档，禁止与 `main` 双向无规则提交。

## 4. 分支保护建议

- `main` 禁止直接 push，至少 1 人评审，CI 全绿才能合并；
- migration、部署、鉴权和数据授权策略变更要求对应 CODEOWNER 评审；
- 发布工作流校验目标 SHA 已属于 `origin/main`；
- 数据库迁移不得自动 downgrade，回滚使用前一镜像加备份/前向修复方案；
- `outputs/` 中需协作的标注与验收资产按既有团队约定保留，但临时目录、密钥和运行备份不得进入 Git。

## 5. 本次决策

当前共享环境继续作为 `phase2-integrated` 发布候选运行，用于三账号联合验收和域名切换。待当前工作树
按主题提交并再次通过门禁后，应立即发起 `phase2-integrated → main` 的发布 PR；合并完成后，从
`main` 的不可变标签重发一次，届时正式把线上来源从集成分支切换为 `main`。
