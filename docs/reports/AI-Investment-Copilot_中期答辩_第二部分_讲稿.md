## 开场与承接（约 20 秒）

各位老师好，前面介绍了产品要解决的问题和整体设计。接下来我汇报第二部分，重点回答三个问题：第一，这个产品在技术上是怎样组织起来的；第二，第一阶段到底已经实现并验证了什么；第三，为什么下一阶段要重点建设动态知识库和 RAG。

我想先说明，我们并不是要做一个直接给出买卖建议的模型，而是要做一个面向主动权益研究的智能协作系统：把研究员的投资逻辑结构化，把后续资料和事件持续关联到具体假设，并且让每一条重要结论都可以引用、复核和追溯。

## 第 1 页：整体架构（约 2 分 30 秒）

### 核心句

这一页最重要的结论是：我们的系统不是“一个大模型加一个网页”，而是围绕投资逻辑全生命周期搭建的分层系统；AI 负责生成候选，规则负责确定性计算，人负责正式决策。

### 可直接照读的讲稿

请看这一页的整体架构。我们的核心设计对象是 Investment Thesis，也就是投资逻辑。围绕一条投资逻辑，系统管理逻辑本身、关键假设、指标、历史证据、状态变化、版本和审计记录。因此，右侧所说的“核心引擎”并不是某一个模型，而是投资逻辑从创建、验证、变化到复盘的完整生命周期。

从下往上看，最底层是数据资源层。这里使用 PostgreSQL 保存结构化业务对象，使用 pgvector 保存版本化向量，使用 MinIO 保存上传的原始文件；同时记录解析切片、处理运行、数据版本和血缘关系。这样做的目的是：系统不只保存 AI 的最终一句话，而是保存这句话来自哪份资料、哪个版本、哪个位置，以及当时使用了什么处理流程。

上一层是 RAG 上下文层。这里的上下文不只是通用知识库，而是四类与投研直接相关的内容：当前投资逻辑、已经确认的假设和指标、历史证据，以及公司和行业资料。RAG 的作用，是在生成候选分析前，为 Agent 找到可引用的上下文；它不负责替代权限判断，也不负责直接决定正式状态。

再上一层是 AI 与规则层。这里我们刻意把 AI 和确定性计算分开。Agent Runtime、模型网关和 Retriever 负责文本理解、草稿生成、事件影响解释和证据组织；同比、环比、预期差、阈值、连续期和失效条件，则由 `app.calc` 中的确定性代码计算。这样即使更换模型或提示词，关键数值口径也不会跟着漂移，历史结果也可以复算。

应用服务层负责把这些能力编排成真实业务流程。例如，资料上传后不是在一次 HTTP 请求里全部完成，而是先形成持久任务，再由 ARQ Worker 和 Redis 队列执行解析、切片、事件抽取、变化处理和失败重试。也就是说，即使模型或解析器暂时失败，任务和原始资料也不会静默丢失。

最上面是用户交互层。我们已经形成 React Web、FastAPI Router、Pydantic 数据契约，以及鉴权和权限过滤。用户在页面上看到的是工作台、变化雷达、投资逻辑、复核复盘和资产治理；背后所有操作都通过服务层进入领域对象，而不是页面直接操作数据库。

最后请看底部的架构原则。第一，依赖只向下，避免业务规则被界面或基础设施反向绑架；第二，API 不直接连接数据库，而是经过服务层和权限校验；第三，AI 不计算关键数值；第四，正式状态只能由人工确认。这里的“人工闸门”不是临时补丁，而是产品架构的一部分。

### 转场句

有了这套分层以后，下一步就不是看我们画了多少模块，而是看这些模块有没有形成真正可运行、可验证的闭环。第二页展示的就是第一阶段已经落地的内容。

## 第 2 页：已实现的内容（约 3 分 30 秒）

### 核心句

第一阶段已经跑通“建卡”和“变化”两条业务闭环，并建立了真实数据评测基线；当前工程链路已经成立，但方向判断仍是主要效果瓶颈。

### 可直接照读的讲稿

这一页上方有两条主流程。

第一条是“建卡闭环”。研究员上传资料或输入研究观点后，系统先完成解析和切片，再由 AI 生成结构化草稿。草稿包括核心观点、假设、指标、风险和失效条件，但它仍然是候选内容。研究员需要编辑、完成发布检查并人工发布，才会形成正式的投资逻辑版本。也就是说，AI 可以帮助研究员从非结构化材料快速形成第一版框架，但不能代替研究员发布正式观点。

第二条是“变化闭环”。新资料进入系统后，系统抽取事件，召回相关逻辑和假设，进行影响分析，再交给确定性规则计算和人工处置。这里“影响分析”和“规则计算”是两个不同环节：AI 可以判断一条事件可能支持、冲突还是中性，并解释传导路径；但是阈值是否突破、连续多少期、组合失效条件是否满足，必须由规则计算。最终，人工可以接受、拒绝或修改系统建议，并填写原因，之后才形成正式状态、版本快照和审计记录。

在工程底座方面，目前 API、Worker、Web 和 Redis 的运行编排已经具备；主数据使用 PostgreSQL，向量检索使用 pgvector，数据库迁移使用 Alembic；原始资料进入 MinIO，并用 SHA-256、对象版本和 Object Lock 保证可追溯性；OpenAPI、JSON Schema 和持续集成用于约束接口和输出质量。这意味着现在展示的不是一组互不连接的 Demo 页面，而是前端、后端、异步任务、数据库、对象存储和 AI Runtime 已经接在同一条链路上。

左下角是独立金标评测结果。这里一共是 59 条盲标样本，覆盖三类行业和九家公司。事件筛选的 Precision 是 96.3%，也就是系统筛出来的 27 条里有 26 条是相关事件；Recall 是 86.7%，也就是 30 条应该召回的事件里召回了 26 条，仍有 13.3% 的漏检。证券归属在当前样本上是 59/59，但我们只把它表述为“当前样本通过”，不能外推为所有市场和所有证券都达到 100%。

假设匹配准确率是 71.2%，说明系统已经可以辅助把事件挂接到具体研究假设，但仍然需要人工纠错。方向判断准确率只有 30.8%，这是第一阶段最重要的效果瓶颈。进一步分析发现，问题主要不是筛选词表，而是很多公告标题本身没有方向信息，必须进入正文读取营业收入同比、销量或交付量同比等事实，才能判断究竟是支持还是冲突。因此，这个结果没有被我们隐藏，而是直接转化为下一阶段加强正文事实抽取和检索质量的依据。

页底的“三行业九家公司、45 条逻辑、135 条假设、450/450 条可追溯证据”，说明我们已经用真实公开数据跑通了跨行业的证据链。这里需要特别澄清：450/450 表示 450 条挂载证据都可以回到来源和定位，不表示 450 条都已经由真实研究员确认。该轮数据中有 168 条已确认、282 条仍待人工处理。因此，这个数字证明的是可追溯链路成立，不是自动判断效果已经成熟。

综合来看，第一阶段的准确表述是：核心工作流已经达到可运行、可测试、可恢复、可评测的工程化 MVP；但还不能称为生产级投研平台，更不能据此宣称已经证明了 Alpha 或投资收益。

### 转场句

从这些结果可以看到，下一阶段的关键不再是简单增加更多页面，而是提高“找到正确证据、组织正确上下文、给出可引用候选结论”的能力。这就是我们把动态知识库和 RAG 作为后续重点的原因。

## 第 3 页：后续重点——动态知识库与 RAG（约 3 分钟）

### 核心句

我们建设 RAG 的目标不是做一个更大的文档搜索框，而是让每一条 AI 候选结论都回到明确的检索范围、原文片段、模型和提示词版本，并始终保留人工决策边界。

### 可直接照读的讲稿

这一页可以分成上、中、下三部分来看。

最上方是 RAG 的目标形态。第一步是资料进入：采集行业和公司资料后，完成解析、切片、去重、事实与事件抽取，并对引用位置和数据质量进行检查。第二步是分层检索：检索范围不是全库漫游，而是先限定当前投资逻辑和已确认假设，再检索当前公司的历史资料和事件，最后补充所属行业的共性知识和变量。第三步才是 Agent 输出：它需要说明影响的是哪一条既有假设、方向和强度如何、置信度是多少，并给出可以打开的原文引用。

中间 A 区是当前已经跑通的确定性流程：资料接入、解析抽取、逻辑关联、影响分析、质量与规则，最后进入人工闸门。B 区是当前的受控 RAG 子系统。它首先按权限、证券和披露时点做前置过滤，然后将全文检索和 pgvector 向量检索进行混合召回，再做证据重排和引用校验。这里最重要的设计顺序是“先过滤、再排序”，不能先召回敏感内容，再在页面上删除，否则摘要或排序过程本身就可能造成权限泄漏。

当前试点结果是 Recall@10 为 61.0%，Top-1 引用正确率为 30.5%，受限身份下越权结果为 0。这个结果说明权限优先的混合检索链路已经成立，而且明显优于当前长查询关键词基线；但 30.5% 的首条引用正确率还不够支撑自动发布。所以当前 RAG 默认关闭，只在显式开启和稳定采样的小流量场景中，为 Agent 提供最多几条候选上下文。

图中的 DeepSeek 表示我们已经具备 OpenAI-compatible 的模型接入能力，可以通过 Gateway 切换外部模型；它不等于当前 RAG 评测指标来自 DeepSeek。当前召回评测使用的是可复现的 256 维字符二元组哈希 embedding 加 pgvector，DeepSeek 配置与密钥保存在本地隔离配置中，第一阶段主要验证接口和结构化输出契约，不能把两者混为一谈。

最下方 C 区是演进路线。P0 是基础增强：补充双人标注和更可靠的评测集，引入正式中文 embedding 与重排模型，改善 Query 构造，并保留每个模型和向量版本。P1 是 Agentic RAG：让 Agent 根据任务拆分查询，循环检索、发现证据缺口、补充检索，并设置成本和停止条件。P2 才是 Graph RAG：把事件、事实、业务变量、指标和投资假设组织成图关系，再将图路径和文本证据融合。需要强调，Agentic RAG 和 Graph RAG 是后续规划，不是当前已经完成的能力。

无论技术怎样演进，最底部的边界不会变化：权限和时间优先过滤，RAG 只提供候选上下文，每条关系都能回到原文，AI 不直接写正式状态，高影响输出必须由人工确认。我们希望增强的是证据获取和关系推理能力，而不是扩大 AI 的自动决策权限。

### 收束句

所以，第一阶段完成的是一个可信的投研协作底座：逻辑可以结构化，资料可以持续进入，事件可以关联到假设，关键数值可以复算，正式变化需要人工确认，历史过程可以追溯。下一阶段我们将重点补齐正文事实抽取、RAG 引用质量、双人标注、正式身份与可观测性，并通过小流量真实用户试点验证它能否真正减少研究员的信息整理和复核成本。

## 现场压缩版（总计约 5～6 分钟）

如果现场时间被压缩，每页只保留下面三段：

1. **架构页：**我们的系统不是“大模型加网页”，而是围绕投资逻辑生命周期搭建的分层架构。AI 只做文本理解和候选生成；同比、阈值、连续期和失效条件由确定性代码计算；正式发布、证据确认和状态变化必须经过人工闸门。所有资料、版本、引用和审计信息都会被保存，确保结果可复算、可追溯。
2. **实现页：**第一阶段已经跑通建卡闭环和变化闭环，并接通 React、FastAPI、Worker、PostgreSQL/pgvector、Redis 和 MinIO。59 条独立金标中，事件筛选 Precision 为 96.3%、Recall 为 86.7%，假设匹配为 71.2%，方向判断只有 30.8%，因此当前主要瓶颈是读取正文后判断事件方向。三行业九家公司形成 45 条逻辑、135 条假设和 450 条可追溯证据，但其中仍有大量候选等待人工处理。

## 答辩表述红线

- 不说“已经实现自动投资决策”，应说“生成候选证据、候选关系和状态建议”。
- 不说“450 条证据全部人工确认”，应说“450 条证据全部可追溯，其中 168 条已确认、282 条待人工处理”。
- 不说“方向判断已经可用”，应说“方向判断 30.8%，是当前主要效果瓶颈”。
- 不说“证券归属普遍达到 100%”，应说“当前 59 条独立样本上为 59/59”。
- 不说“RAG 已经上线”，应说“默认关闭、稳定采样的小流量候选上下文试点”。
- 不说“DeepSeek 产生了当前 RAG 指标”，应区分“模型生成 Provider”和“检索 embedding/pgvector 评测”。
- 不说“Graph RAG 已实现”，应说“属于 P2 演进路线”。
- 不说“已经证明 Alpha”，应说“当前验证的是工作流、可追溯性和效果基线，不是投资收益”。
