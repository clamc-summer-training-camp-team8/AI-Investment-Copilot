## 1. 技术摘要

AI Investment Copilot 第一阶段采用模块化单体架构，实现 React 前端、FastAPI API、领域服务、
异步 Worker、PostgreSQL/pgvector、Redis/ARQ 和 MinIO 对象存储。系统围绕 Investment Thesis
领域对象设计，刻意将 AI 语义任务与确定性金融计算分离，并通过人工闸门、版本快照、时间语义、
权限过滤和审计日志控制 AI 的业务边界。

当前工程基线包含 36 张 ORM 表、11 个顺序迁移、54 个 OpenAPI 路径、57 个 HTTP 操作和
67 个 API Schema。第一阶段的最终门禁包括 329 个通过的单元/契约测试、42 个通过的数据库
集成测试、6 条保持有效的分层依赖契约，以及通用前端和固定场景前端各自的 lint、类型检查
与生产构建。

技术结论为：**核心架构、数据链路、版本治理、恢复能力和评测基础已经适合工程化 MVP；正式
共享部署仍需补齐身份集成、可观测性、跨机器灾备和容量验证。**

## 2. 设计原则

### 2.1 业务对象先于技术组件

系统不是按 Controller/Service/DAO 简单平铺，而是围绕投资逻辑的生命周期划分职责。架构
直接支撑以下对象关系：

```text
Security
  └─ Thesis
       ├─ Hypothesis
       │    ├─ MetricMapping ── MetricObservation
       │    └─ EvidenceRelation ── Evidence ── Event ── Document
       ├─ StatusSuggestion ── HumanDecision
       ├─ ReviewTask
       └─ ThesisVersion / RevisionDraft / AuditLog
```

### 2.2 AI 与确定性计算严格分离

`app/ai` 负责文本理解、草稿生成、事件抽取和影响解释；`app/calc` 负责同比、环比、预期差、
趋势、分位、阈值和连续期判断。AI 不计算正式数值，确定性计算不依赖模型、数据库或网络。

该边界带来三项直接收益：

1. 金融数值和状态规则可以脱离模型做精确单元测试；
2. 更换模型或提示词不会改变计算口径；
3. 历史结论可以按数据、规则和版本重新计算。

### 2.3 所有高影响输出保留人工闸门

AI、RAG 和规则只生成草稿、候选关系或状态建议。正式发布、证据确认和状态变更必须由人工
执行；状态处置要求记录操作人、动作和原因。系统不会因模型置信度高而跳过该流程。

### 2.4 时间、版本和权限是数据模型的一部分

时间和权限不作为 UI 层附加条件，而是参与数据存储和查询：

- 分离事实发生、披露、入库和生成时间；
- 历史状态复算按逻辑建立日和复算时点裁剪；
- 原件、处理运行、衍生产物、逻辑和向量分别版本化；
- 权限在服务层计算，并在检索排序前过滤。

### 3.1 逻辑分层

本地 Docker Compose 只编排 PostgreSQL、Redis 和 MinIO；`scripts/dev.ps1` 启动依赖后执行
迁移、初始化 bucket，并启动 API、Worker 和 Web。`/health/ready` 同时检查数据库、队列、
Worker 心跳和对象存储，避免把“API 进程存活”误认为系统可用。

### 3.3 模块化单体的选择

MVP 未拆成微服务，原因是当前复杂度主要在领域边界而非独立扩缩容。通过 import-linter 保持
模块依赖方向，将来可按模块切分服务，同时避免第一阶段过早承担服务发现、分布式事务、消息
一致性和跨服务调试成本。

```text
├─ ai/            模型网关、Provider、提示词和契约校验

├─ schemas/       API DTO
├─ api/           FastAPI 路由和鉴权
└─ workers/       异步任务与周期任务

contracts/        JSON Schema、OpenAPI 与跨模块契约
web/              React 前端

scripts/          开发、数据治理、备份与恢复工具
```

### 5.2 机器化依赖规则

当前 6 条 Import Linter 契约包括：

1. 后端依赖只能由上层指向下层；
2. `app.calc` 必须保持纯函数边界；
3. `app.core` 不得依赖兄弟模块；
4. `app.api` 不得直连数据层；
5. `app.ingest` 解析阶段不得调用模型；
6. 线上 `app/` 不得依赖离线 `analytics/`。

这些规则能防止 API 绕过权限与审计、计算模块引入 IO、实验代码进入线上请求等高风险退化。

### 6.5 不可变与追加式设计

```text
document
  └─ document_revision（原件、哈希、对象版本、来源、授权）
       └─ ingestion_run（处理组件版本、状态、时间、质量摘要）
            ├─ segment artifact
            ├─ fact artifact
            ├─ event artifact
            ├─ activity search index
            └─ versioned embedding
```

重新处理只创建新的 `ingestion_run`，不会覆盖旧产物；新 embedding 使用新版本写入，不覆盖旧
向量；搜索索引是可重建投影，不作为事实源。

## 7. 数据库迁移与一致性

迁移链从 `0001_initial_schema` 顺序演进至 `0011_ai_runtime_observability`，保持单一 head。关键演进：

1. `0001`：核心业务、版本、审计和质量表；
2. `0002`～`0005`：证据字段、多关系、文档事实和裁决；
3. `0006`：逻辑草稿建议字段；
4. `0007`：持久任务与摄取可靠性；
5. `0008`：研究资产、运行级产物和权限检索索引；
6. `0009`：资产生命周期与修订闭环；
7. `0010`：pgvector 扩展、256 维版本化 embedding 和 HNSW 余弦索引。

第一阶段完成临时数据库 `upgrade head → downgrade base → upgrade head` 验证。CI 也会检查
多 head 并执行迁移往返，避免两个分支引入分叉迁移。

## 8. 关键业务链路

### 8.1 建卡与发布链路

```text
Web 创建逻辑
  → POST /theses/drafts
  → AI Gateway 生成结构化草稿
  → JSON Schema 校验与必要修复
  → 保存可编辑 Thesis/Hypothesis/Metric Mapping
  → 发布就绪检查
  → 负责人确认发布
  → ThesisVersion V1 + AuditLog
```

AI 不得擅自填写研究员正式预期或阈值。发布就绪检查验证必填字段、核心假设、负责人、版本和
关键关系，只有人工动作能进入正式版本。

### 8.2 新资料摄取链路

```text
multipart 上传
  → 文件大小/类型/时间/身份校验
  → MinIO 不可变原件 + version ID + SHA-256
  → PostgreSQL Document / Revision / Job
  → Redis 入队（稳定 job_id）
  → Worker 从对象存储受控下载到 processing spool
  → PDF/DOCX/TXT/OCR/表格解析
  → 语义切片与质量检查
  → 事件抽取、证券归属、假设匹配
  → 候选 Evidence / Relation / Review
  → 运行产物、检索索引、embedding、审计
```

对象存储或 Worker 不可用时 API 返回 503，不会退化为保存开发机绝对路径后伪装成功。

### 8.3 事件到假设链路

1. 事件使用稳定指纹去重；
2. 证券归属限制候选范围；
3. 规则和可选 RAG 召回相关逻辑/假设；
4. AI 生成相关性、方向、强度、事实摘要、传导路径和引用；
5. 低置信或无法匹配结果进入人工队列；
6. 候选证据进入变化雷达；
7. 人工确认后才进入正式证据链。

### 8.4 状态建议链路

```text
已确认证据 + 指标观测 + 阈值 + 连续期 + 复核日
  → summarize_evidence
  → check_invalidation（建立日与复算时点双向裁剪）
  → evaluate_thesis_invalidation（AND/OR 组合条件）
  → suggest_status
  → status_suggestion_log（不改正式状态）
  → 负责人接受/拒绝/修改并填写原因
  → 正式状态 + ThesisVersion + AuditLog
```

`apply_decision` 是正式状态变更入口；它检查动作、原因、建议归属、重复处置和合法状态流转。

## 9. 文档解析与数据质量

### 9.1 解析能力

- PDF 文本层提取；
- pdfplumber 辅助页级定位；
- 扫描页 RapidOCR；
- DOCX 段落与表格解析；
- TXT 文本解析；
- 语义切片、页码/段落 locator 和 extraction method；
- 结构化事实与事件产物。

### 9.2 质量降级

质量检查识别空文档、内容过少、解析异常、OCR 低质量、证券歧义、假设无法匹配和模型低置信。
阻断性问题停止自动链路并创建人工复核；非阻断问题随运行产物保留。

### 9.3 防未来信息泄漏

系统分别保存事件发生时间、披露时间、入库时间和生成时间。指标观测使用真实披露日或保守
兜底值作为可得时间。历史状态复算同时排除逻辑建立日前数据和复算时点后的数据。RAG 事件
试点也只检索事件披露时点以前的切片。

该设计源于真实缺陷：此前以法定截止日代替真实披露日，在 37 期抽查中有 7 期提前使用信息，
最多提前 28 天。修复后该抽查泄漏归零，并通过独立来源回归测试保护。

## 10. AI 网关与结构化输出

### 10.1 Provider 抽象

`Gateway` 通过统一 `Provider` 协议暴露五类任务：

- `thesis_draft`：从观点或资料生成逻辑草稿；
- `extract_events`：从切片提取结构化事件；
- `event_impact`：判断事件与候选假设的关系和方向；
- `metric_explain`：只解释确定性计算结果，不重算或改写数值；
- `review_draft`：基于已提供记录生成阶段复盘草稿。

实现包括：

- `LocalProvider`：离线确定性规则，保证无模型端点时产品可运行；
- `MockProvider`：测试和受控演示使用，可注入固定载荷，不调用网络；
- `HttpProvider`：OpenAI-compatible Chat Completions，支持端点、密钥、超时、有限重试、输出
  token 上限和 thinking 配置。

提示词不再只由 Python 常量维护。逻辑草稿、事件影响、指标解释和复盘草稿均由版本化
`app/ai/skills/*/SKILL.md` 加载；事件影响保留 `mentor-ruling-v1-20260811` 的业务裁决规则。
HTTP Provider 将精简后的完整 JSON Schema 注入 system message；第一次输出失败时，网关把
契约或引用错误作为受控修复指令再调用一次。

### 10.2 输出契约

模型输出必须通过 `contracts/ai/` JSON Schema。网关执行：

1. 渲染带版本提示模板；
2. 调用 Provider；
3. 解析 JSON；
4. 执行一次受控修复；
5. 进行 Schema 和置信度校验；
6. 失败时转人工或任务重试，不静默写入正式对象。

### 10.3 模型安全与审计

- API Key 使用 `SecretStr`，只由 `.env` 或密钥系统注入；
- 日志不写 API Key、完整提示词或供应商原始响应；
- 审计仅保留必要的模型、提示词、usage、耗时和安全裁剪后的错误信息；
- 未配置 token 单价时成本保持 `null`，不推测费用；
- 模型不可用时任务有边界重试，原始输入和持久任务不丢失。

### 10.4 Agent Runtime 与证据校验

`InvestmentResearchAgent` 为逻辑草稿、事件影响、指标解释和阶段复盘提供统一执行状态机：

```text
created → retrieving → generating → verifying
        → completed / needs_human_review / degraded / failed
```

事件 Agent 在证券、披露时点和文档标签约束下检索候选片段；`EvidenceAgent` 校验引用是否属于
允许集合，并对来源权威性、时效性、事实覆盖、交叉来源和传导路径计算可解释分项。证据校验
失败可以触发一次引用修复，但结果仍保持候选并进入人工复核。

Worker 使用稳定幂等键构造 Runtime run ID，并注入 `SqlRuntimeRecorder`。状态转换和最终候选
信封写入 `ai_run`，归一化后的模型 token、耗时、请求 ID、尝试次数和可选成本写入
`model_call_log`。价格未配置时成本为 `NULL`，不把未知成本记成零。

## 11. RAG 与混合检索试点

### 11.1 向量模型与版本

第一阶段使用 `hash-char-2gram-v1` 作为可复现的 256 维离线基线。它通过字符二元组哈希构造
归一化向量，目标是验证数据结构、权限过滤、混合排序和评测方法，而非代表生产语义效果。

`segment_embedding` 以 `(index_id, embedding_version)` 唯一，关联 `ingestion_run_id`，允许
并存多个 embedding 版本。HNSW 使用 `vector_cosine_ops`。

### 11.2 权限优先混合排序

混合检索执行顺序：

1. 根据 `Actor.document_labels` 过滤可见性；
2. 根据证券、行业有效期和披露时间过滤；
3. 连接指定 embedding 版本；
4. 计算 PostgreSQL `ts_rank_cd`；
5. 计算 pgvector 余弦相似度；
6. 按可配置权重合成排序；
7. 返回关键词分数、向量分数、处理运行和 embedding 版本。

默认权重为关键词 0.45、向量 0.55。权限过滤在排名前执行，检索不能先召回再在应用层删掉
越权内容。

### 11.3 两类受控入口

- 新建逻辑：只有研究员显式勾选时才检索同证券、当前身份可见的候选上下文；
- 事件→假设：`RAG_EVENT_PILOT_ENABLED=false` 默认关闭，开启后按事件稳定哈希采样，默认
  5%，最多取 3 条披露时点前、同证券、可见切片。

RAG 不参与鉴权、事件去重、确定性计算、失效判断和正式状态变化。

### 11.4 评测结果与判断

独立信息需求 59 条：混合检索 Recall@5 57.6%、Recall@10 61.0%、MRR 0.4136、Top-1 引用
正确率 30.5%、越权结果 0。结论是安全试点链路成立，但效果不满足扩量，默认关闭是必要的。

## 12. 权限、安全与合规设计

### 12.1 身份模式

- 本地：`AUTH_MODE=trusted_headers`，仅用于受控开发；
- 非本地：`AUTH_MODE=jwt`，验证 HS256/384/512、issuer、audience、exp、iat 和 sub；
- JWT secret 少于 32 字节时拒绝认证；
- 系统只验证令牌，不在 MVP 内保存密码或签发机构生产令牌。

### 12.2 内容权限

投资逻辑支持私有、团队和授权范围。文档使用公开、内部、内部受限和机密标签。服务层在访问
数据前计算可见性，API 不直接访问仓储。不可见对象返回 404，避免通过 403 枚举他人的研究覆盖。

管理员权限不等于内容访问权；管理员可以做系统治理，但不会自动获得全部研究内容。

### 12.3 证据与来源约束

证据可见范围不得宽于来源文档。内部受限及以上文档不能通过更开放的证据卡片泄露摘要。
权限变化会同步检索投影；墓碑删除会立即移出活动索引。

### 12.4 产品合规边界

- 不生成交易、评级和调仓指令；
- 不把 AI 置信度伪装成投资确定性；
- 正式结论展示来源、引用、模型版本和确认状态；
- 公开披露数据可以版本化复算，非公开、受限原文、个人信息和凭证禁止提交仓库。

## 13. 异步任务与可靠性

### 13.1 持久任务

上传请求先在 PostgreSQL 建立 `document_processing_job`，提交后再投递 Redis。任务使用稳定
`job_id` 防止重复入队，并记录任务所有者，查询和重放受身份限制。

### 13.2 重试和死信

- 可重试错误按指数间隔重试，最长延迟受限；
- 达到上限后持久化失败结果并标记 dead letter；
- 失败产生人工复核项；
- Web 可查看死信并在原件保留期内重放；
- 重放创建新任务，不覆盖失败历史。

### 13.3 Stale recovery 与清理

Worker 每 15 分钟扫描僵死任务，并在启动时立即执行一次。每天执行上传暂存清理；失败原件和
正常原件使用不同保留期。Worker sentinel 参与 `/health/ready`，只有 Redis 可用但无消费者时
系统仍判定未就绪。

## 14. 对象存储、备份与恢复

### 14.1 对象存储

MinIO bucket `copilot-documents` 启用：

- 版本控制；
- Governance Object Lock；
- 非当前版本生命周期策略；
- 按 SHA-256 寻址；
- 数据库保存 object key、version ID、content hash 和来源授权。

上传后 Worker 通过受控接口下载到 `.runtime` processing spool；数据库不保存开发机绝对路径。

### 14.2 备份组成

`scripts/backup_local.ps1` 生成：

1. PostgreSQL custom-format dump；
2. dump SHA-256；
3. 全部数据库对象版本 manifest；
4. 每个对象版本的实际内容副本；
5. 每个内容副本的 SHA-256。

PostgreSQL 本地 Compose 开启 WAL archive，并使用独立 volume。

### 14.3 隔离恢复演练

`scripts/restore_drill.ps1` 在一次性 pgvector PostgreSQL 容器中：

1. 校验备份 manifest 和文件哈希；
2. 执行 `pg_restore --clean --if-exists`；
3. 核对 Alembic head；
4. 交叉比对数据库中的 object key、version ID、content hash 与对象内容；
5. 删除临时容器，不触碰开发数据库。

第一阶段已完成 3 个对象版本的恢复和内容哈希核验。该结果仍不能替代跨机器复制与 PITR 演练。

- 健康与就绪检查；
- 固定场景资料上传、AI 分析投影、引用上下文、假设健康度和结构化时间线。

`scripts.export_openapi --check` 保证代码与 `contracts/api/openapi.yaml` 一致，前端不依赖后端内部
Python 类型。

### 15.2 前端架构

通用 `web/` 使用统一研究上下文选择器和五个一级导航。独立 `web_demo/` 提供中芯国际 2023
年报重大风险固定流程，真实模式只访问实际 API 与 PostgreSQL，并对上传文件做登记哈希校验。
两套应用都使用 TanStack Query 管理服务端状态，生产构建均通过 TypeScript 和 ESLint 门禁。

### 15.3 交互安全

- 高影响操作使用确认对话框；
- 解除关系、驳回或状态变化要求原因；
- 候选与已确认使用不同状态展示；
- 低置信、失败和权限问题不被隐藏为普通空状态；
- 原文 locator、来源、时间和版本在证据详情可追踪。

配置由 Pydantic Settings 从环境读取，`.env.example` 只提供模板，真实 `.env` 不进入 Git。

## 20. 技术债与改进建议

### 20.1 P0：共享试点前必须完成

1. 接入机构 OIDC/JWT、角色和团队同步，建立服务端 RBAC；
2. 建立密钥管理，不在试点主机静态保存数据库、MinIO 和模型密钥；
3. 引入结构化日志、指标、追踪和告警；
4. 完成跨机器备份、WAL/PITR 和恢复目标验证；
5. 执行容量、重启、依赖故障和多实例演练；
6. 对 `contracts/` 和迁移完成消费方评审。

### 20.2 P1：效果与检索

1. 增加第二标注人和一致性指标；
2. 将哈希 embedding 替换为正式中文 embedding，并保留旧版本；
3. 改进查询构造、分段策略、重排和引用对齐；
4. 为每次 RAG 试点保存实验分组、召回集合、人工处置和后续行动；
5. 只有引用正确率和人工采纳指标达标后再扩大采样率；
6. 方向判断继续保留人工，不因召回效果提升而自动化。

### 20.3 P1/P2：数据和集成

1. 接入正式证券、行业、财务和经营数据源；
2. 按来源授权和数据合同管理接入；
3. 自动公告/新闻流复用现有任务、指纹和人工闸门；
4. 组合视图只做聚合，不在本系统内生成组合优化；
5. 因子与复杂回测对接专业平台，而非在 MVP 中重复建设。

## 21. 推荐的技术演进路线

```text
当前：模块化单体 + 本地完整环境 + 受控 RAG
  │
  ├─ P0-4：OIDC/RBAC + secrets + observability + cross-machine DR
  │
  ├─ 小规模试点：真实用户、真实授权资料、运营指标、5% RAG 分流
  │

```

在出现明确的独立扩缩容或组织边界之前，不建议仅为“技术先进性”拆微服务。优先保持领域边界、
契约和数据一致性，将可观测性和部署标准化做好。

## 23. 结论

第一阶段的技术建设已经把产品边界转化为可执行架构：AI 与计算分离，权限在服务层统一过滤，
新资料通过持久任务和对象存储处理，状态只经人工动作改变，所有重要结果保留时间、来源、版本
和审计。pgvector 和 RAG 被限制在候选上下文，效果不足时可以关闭而不影响核心业务闭环。

系统当前具备继续开发和受控试点准备的可靠基础，但正式共享部署仍取决于身份、可观测性、跨机
灾备和容量门槛。技术演进应保持“安全与可复算优先于自动化范围，真实用户指标优先于功能数量”
的原则。
