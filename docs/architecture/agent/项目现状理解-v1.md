# 项目现状理解 v1

> 基线：`phase1-integrated`，提交 `92571cd`。本文依据真实调用链整理，不以 README 命名推断实现。

## 1. 一句话目标

系统围绕 Investment Thesis 和 Research Hypothesis，将公开研究资料处理为可追溯 Evidence、Metric 观察和 AI 候选判断，经研究员确认后形成可版本化、可审计的研究资产。

## 2. 当前真实架构

```text
Frontend（web / web_demo）
  → FastAPI Backend
    → PostgreSQL / pgvector（业务对象、检索索引、版本与审计）
    → Redis / ARQ Worker（文档异步处理）
    → MinIO（原文归档）
    → Agent Runtime / Gateway
       → Retriever
       → Local / Mock / HTTP LLM Provider
       → Schema Validator / Evidence Validator
```

Backend 是业务流程编排器；Agent 是受 Backend 调用的 AI 任务编排器；RAG 是可追溯资料召回能力。

## 3. 核心对象

```text
Security
└── Thesis
    ├── Hypothesis
    │   └── HypothesisMetricMap
    │       └── Metric / MetricObservation
    ├── EvidenceRelation ── Evidence
    ├── ThesisVersion
    ├── StatusSuggestionLog
    └── AuditLog
```

- **Thesis**：投资逻辑正式对象，保存核心观点、状态、负责人、版本和复盘时间。
- **Hypothesis**：可验证研究假设，保存观察窗口、失效规则和重要性。
- **Evidence**：由资料和事件产生的事实及候选影响，保留来源、locator、方向、强度和确认状态。
- **Metric**：通过映射关联假设，保存期望方向、阈值、连续触发期数和观察值。

Agent 只生成候选内容；正式状态、版本和人工确认均由 Backend 管理。

## 4. Agent 当前职责

总入口为 `app/ai/runtime.py::InvestmentResearchAgent`：

| 能力 | 实现 | 当前接入情况 |
|---|---|---|
| 投资逻辑草稿 | `ThesisDraftAgent` | API 有同类能力，但直接调用 Gateway，未走完整 Runtime |
| 事件影响分析 | `InvestmentLogicChangeAgent` | 已接入文档 Worker 主链 |
| 指标解释 | `MetricExplainAgent` | 仅库能力和测试，未接正式 API/Worker |
| 定期复盘草稿 | `ReviewAgent` | 仅库能力和测试，未接 Scheduler/API |
| 引用和证据校验 | `EvidenceAgent` | 已接 Runtime，属于确定性校验器 |

当前不是自主 Agent：没有 Planner、自由工具选择、长期记忆或自主状态更新。其执行顺序由 Backend/Worker 固定编排。

## 5. RAG 当前职责

- 文档解析后建立关键词索引与向量索引。
- PostgreSQL 全文检索与 pgvector 混合召回。
- 按权限、证券、行业、发布时间和删除状态过滤。
- 返回 `document_id`、`locator`、`content`、得分及索引版本。
- Agent 用 locator 形成 Citation，Evidence 校验器检查引用是否属于允许结果。

当前 Embedding 是 256 维确定性 `hash-char-2gram-v1` 基线；没有独立 Reranker。事件 RAG 默认为关闭的 5% Pilot。

## 6. Backend 当前职责

- FastAPI 接口、用户身份和权限。
- Thesis/Hypothesis/Evidence/Metric 生命周期。
- 数据库事务、正式状态、人工门禁、版本和审计。
- 文档上传、MinIO 归档、Redis/ARQ 异步任务。
- 组装 Agent 输入并持久化候选结果。

Agent 核心代码不访问数据库，Backend/Worker 通过 Unit of Work 和 Repository 完成持久化。

## 7. 最完整业务流程

```text
POST /api/jobs/documents
  → 原文归档并创建 ingestion run / job
  → ARQ Worker 解析 PDF/DOCX/TXT（PDF 可 OCR）
  → 段落/表格切片并生成 locator
  → 保存 Document / Segment / Fact / Event
  → 创建关键词和向量索引
  → 按证券召回已发布 Thesis 与 Hypothesis
  → 规则匹配目标 Hypothesis
  → Agent 判断支持/冲突/中性/待定
  → Citation、Schema 与一致性校验
  → 保存候选 Evidence / EvidenceRelation / StatusSuggestion
  → 研究员确认
  → Backend 更新正式状态、版本和审计
```

## 8. 已实现

- 投资逻辑、假设、指标、证据和版本的数据模型。
- 文档上传、归档、解析、OCR、切片和原文定位。
- 关键词与向量混合检索及权限过滤。
- 事件抽取、事件与假设匹配、候选影响判断。
- JSON Schema、引用、证据质量和一致性校验。
- 人工审核、状态建议、正式状态更新和审计。
- ARQ 异步任务、失败重试和任务恢复。

## 9. 尚未实现或未正式接通

- 自动新闻/公告持续采集。
- 生产级语义 Embedding 和独立 Reranker。
- 全量事件 RAG。
- Metric Tool 和自动指标数据更新。
- ReviewAgent 的定时触发。
- Agent 自主规划、自由工具调用和长期记忆。
- 假设之间的自动级联传播。
- Agent 自动修改或发布正式业务状态。

## 10. 容易误解的实现

- `web_demo` 中芯国际流程是固定文件哈希和预置分析结果，不代表通用 Agent 现场推理。
- `document_chain.draft_from_document()` 当前没有生产调用方。
- `app.ai.retrieval.HybridRetriever` 当前主要用于测试；正式混合检索走资产服务和 Repository SQL。
- `real_data/` 不会被在线后端自动扫描入库；主要用于测试、离线实验和固定演示。
- `MetricExplainAgent`、`ReviewAgent` 有实现和测试，但尚未产品化。

## 11. Agent 开发者必须确认的问题

1. Thesis Draft 的唯一正式入口是 Runtime 还是 Gateway 直调？
2. 新文档只更新已有逻辑，还是允许创建新逻辑草稿？
3. Agent 能建议哪些字段，哪些字段必须人工填写？
4. 一个事件是否允许同时关联多条假设？
5. 假设之间是否需要父子依赖和级联建议？
6. Metric 数据由谁获取、计算和版本化？
7. RAG 正式启用的质量门槛是什么？
8. ReviewAgent 由定时任务还是用户操作触发？
9. 人工确认后需要形成 Evidence、Hypothesis 还是整个 Thesis 的新版本？
10. 生产环境使用何种 Embedding、Reranker 和外部金融数据源？
