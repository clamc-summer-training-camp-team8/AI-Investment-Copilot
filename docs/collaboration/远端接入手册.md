# 远端接入手册

平台：GitHub，仓库归组织所有。协作模型见 [`README.md`](README.md)，决策背景见 [ADR-0005](../adr/0005-按团队规模裁剪评审强度.md)。


## 总览

| 步骤 | 做什么 | 谁 | 大约耗时 |
| --- | --- | --- | --- |
| 1 | 建组织与两个 team | 管理员 | 5 分钟 |
| 2 | 建私有仓库（空库，不要初始化） | 管理员 | 2 分钟 |
| 3 | 配置认证并推送现有 9 个提交 | 管理员 | 10 分钟 |
| 4 | 等 CI 跑完一次，确认 job 名字 | 管理员 | 5 分钟 |
| 5 | 配分支保护 | 管理员 | 10 分钟 |
| 6 | 替换 `CODEOWNERS` 占位符 | 管理员 | 5 分钟 |
| 7 | 用一个真 PR 验证整条链路 | 管理员 | 10 分钟 |
| 8 | 邀请成员 | 管理员 | 5 分钟 |
| 9 | 成员上手 | 每个人 | 15 分钟 |

**顺序不能乱的地方**：第 4 步必须在第 5 步之前（没跑过的 CI job 在分支保护的下拉框里搜不到）；第 5、6 步必须在第 8 步之前（没有保护就拉人进来，等于裸奔的 `main`）。

## 1. 建组织与 team（管理员）

组织免费版对私有仓库就支持分支保护和 code owners，不用付费。

1. 打开 https://github.com/organizations/plan，选 Free，填组织名（下文用 `your-org` 代指）。
2. 进 `Settings → Teams`，建两个 team：

| team | 成员 | 用途 |
| --- | --- | --- |
| `maintainers` | 你 + 至少 1 名熟悉架构的成员 | 契约、迁移、分层约束的把关 |
| `product` | 你 + 需求负责人 | 需求基线文档的把关 |

**每个 team 至少两人。** 单人 team 会死锁：作者不能 approve 自己的 PR，如果某路径只有一个 owner 且他就是作者，这个 PR 永远合不进去。人少的话你自己同时进两个 team，另一个人也进两个，就够了。

一个人可以同时属于多个 team。

## 2. 建空仓库（管理员）

在组织页面点 `New repository`：

- Owner 选 **组织**，不是你的个人账号
- 名字建议 `ai-investment-copilot`
- **Private**
- **不要**勾 Add a README / .gitignore / license

最后一条很重要。勾了会在远端产生一个初始提交，和本地 9 个提交没有共同祖先，推送时报 `rejected (fetch first)`，然后你会被迫用 `--force` 或者 `--allow-unrelated-histories`，把干净的历史搞乱。空库直接推最省事。

建完页面会显示 `git remote add origin ...`，先别执行，下一步要先解决认证。

## 3. 配置认证并推送（管理员）

GitHub 不接受账号密码推送，两种方式选一个。

### 方式 A：SSH（推荐，配一次长期有效）

```bash
ssh-keygen -t ed25519 -C "你的邮箱"        # 一路回车，passphrase 可留空
cat ~/.ssh/id_ed25519.pub                  # 复制输出
```

把公钥贴到 https://github.com/settings/keys 的 `New SSH key`。验证：

```bash
ssh -T git@github.com
# 看到 "Hi <用户名>! You've successfully authenticated" 即可
# 首次连接会问 fingerprint，输 yes
```

### 方式 B：HTTPS + Personal Access Token

在 https://github.com/settings/tokens 建 fine-grained token，勾 `Contents: Read and write`、`Pull requests: Read and write`，设过期时间。推送时用户名填 GitHub 用户名，密码填 token。

```bash
git config --global credential.helper store   # 避免每次都输
```

注意：token 会明文存在 `~/.git-credentials`。共享机器上别用这个方式。

### 推送

```bash
cd /mnt/4x4t/liaojun/product

git remote add origin git@github.com:your-org/ai-investment-copilot.git
# HTTPS 方式则用 https://github.com/your-org/ai-investment-copilot.git

git push -u origin main
```

推之前确认两件事：

```bash
git status                # 应显示 nothing to commit
git log --oneline | wc -l # 应该是 9（或你后续提交后的数量）
```

推完刷新仓库页面，应该能看到 9 个提交、117 个文件，以及渲染好的 README。

## 4. 等 CI 跑完一次（管理员）

推送会自动触发 `.github/workflows/ci.yml`。打开仓库的 `Actions` 标签看结果。

**必须等这一步跑完再配分支保护**：GitHub 只让你选「至少运行过一次」的 check，没跑过的 job 在搜索框里根本搜不到。

三个 job 的显示名（配分支保护时要搜的就是这几个字符串）：

| job id | 显示名 | 查什么 |
| --- | --- | --- |
| `lint` | 格式与静态检查 | ruff + mypy |
| `arch` | 分层依赖契约 | import-linter + 契约 Schema 合法性 |
| `test` | 测试 | 迁移往返 + 单元/契约/集成测试 |

首次运行如果 `test` 失败，先看是不是集成测试的问题——它需要 CI 起的 PostgreSQL 服务。本地跑 `make check` 是通过的（不含集成测试），所以失败大概率在数据库连接或迁移环节。日志在 Actions 里点开对应 step 看。

全绿之后再往下走。带着红的 CI 配分支保护，会把自己锁在外面。

## 5. 配分支保护（管理员）

进 `Settings → Branches → Add branch protection rule`（或用较新的 `Rules → Rulesets`，选项名一致）。

Branch name pattern 填 `main`，然后按下表勾选：

| 选项 | 设置 | 为什么 |
| --- | --- | --- |
| Require a pull request before merging | ✅ | 唯一的硬要求，整套协作设计靠它 |
| └ Require approvals | **0** | 默认自合，普通改动不等人 |
| └ Require review from Code Owners | ✅ | 只对 `CODEOWNERS` 里那四类路径生效 |
| Require status checks to pass | ✅ | 机器门禁不放过 |
| └ 搜索并添加 | `格式与静态检查`、`分层依赖契约`、`测试` | 第 4 步里的三个显示名 |
| └ Require branches to be up to date | ✅ | 防止两个 PR 分别绿、合起来红 |
| Allow force pushes | ❌ 不勾 | 保护历史 |
| Allow deletions | ❌ 不勾 | 防误删 `main` |

`Require approvals = 0` 配 `Require review from Code Owners` 是关键组合，我确认过 GitHub 的行为：approvals 设成 0 不会让 code owner 规则失效。效果是普通改动零 approve 自合，只有碰到 `contracts/`、`alembic/versions/`、`.importlinter`、`docs/product|data/` 时才要求对应 team 批准。

### 刻意不开的两项

**Require linear history**：会强制作者处理 rebase 冲突，而 squash merge 本身已产生线性历史，开了只是多添麻烦。

**Do not allow bypassing the above settings（管理员也受限）**：2-3 人团队需要有人能在 CI 卡死、GitHub 抽风时救场。等团队大了再开。

### 顺手开一下 auto-merge

`Settings → General → Pull Requests`：

- ✅ Allow auto-merge — 推完 PR 就点上，CI 绿了自动合，不用回来盯着
- ✅ Allow squash merging，并把 **Default to pull request title and description** 选上
- ❌ 关掉 Allow merge commits 和 Allow rebase merging（统一用 squash，主干历史才干净）
- ✅ Automatically delete head branches — 合完自动删分支，省手工清理

## 6. 替换 CODEOWNERS 占位符（管理员）

现在 `.github/CODEOWNERS` 里是 `@your-org/maintainers` 这样的占位符。**占位符状态下 code owner 评审完全不生效**，那四类不可逆路径等于没有保护，而且 GitHub 不会报错，只会静默忽略无效的 owner。

把 `your-org` 换成实际组织名。这个改动本身会触发 code owner 要求（`CODEOWNERS` 自己也在保护列表里），所以走一个正常 PR：

```bash
git switch -c chore/infra-codeowners
# 编辑 .github/CODEOWNERS，把 your-org 换成实际组织名
git commit -am "chore(infra): 填入实际组织 team 名"
git push -u origin HEAD
```

开 PR 后在页面右侧确认 **Reviewers 里自动出现了对应 team**。如果没出现，说明 team 名字写错或者 team 没有 write 权限，回第 8 节的权限表检查。

### 验证 CODEOWNERS 语法

GitHub 在仓库页面直接给了语法检查：打开 `.github/CODEOWNERS` 文件页，如果有语法错误或无效的 team，顶部会显示黄色警告条。**没有警告条才算配对了。**

常见错误：

- 写了 team 但组织里没这个 team → 静默失效
- team 只有 read 权限 → 静默失效，PR 会一直等一个永远不会来的批准
- 个人账号仓库写了 `@org/team` 形式 → 无效（本项目在组织下，不会遇到）

## 7. 验证整条链路（管理员）

拉人进来之前，自己走一遍。**这一步别省**——配错了分支保护，最坏情况是你自己也推不了 `main`。

### 7.1 确认 main 推不动了

```bash
git switch main
echo "" >> README.md
git commit -am "test: 应该被拒绝"
git push origin main
```

期望看到 `remote: error: GH006: Protected branch update failed`。看到就对了，说明保护生效。

```bash
git reset --hard HEAD~1     # 撤掉这个测试提交
```

### 7.2 确认普通改动能自合

```bash
git switch -c docs/collab-smoke-test
# 随便改一行 CONTRIBUTING.md 里的措辞
git commit -am "docs(collab): 验证自合流程"
git push -u origin HEAD
```

开 PR，期望：

- Reviewers **没有**被自动请求（这条路径没有 owner）
- 三个 check 跑起来，全绿后 **Merge 按钮变绿可点**
- 不需要任何人 approve

合掉。这就是团队 90% 情况下的日常流程。

### 7.3 确认四类路径拦得住

```bash
git switch main && git pull --ff-only
git switch -c chore/infra-owner-test
# 在 .importlinter 末尾加一行注释
git commit -am "chore(infra): 验证 code owner 拦截"
git push -u origin HEAD
```

开 PR，期望：

- Reviewers 里**自动出现** `@your-org/maintainers`
- 即使 CI 全绿，Merge 按钮仍显示 **Review required**，点不动

看到这个就说明保护真的生效了。让 team 里另一个人批准，或者你自己删掉这个测试分支：

```bash
git push origin --delete chore/infra-owner-test
```

三条都符合预期，配置就是对的。

## 8. 邀请成员（管理员）

### 权限

`Settings → Collaborators and teams`，或在组织的 team 页面加人。

| 角色 | 仓库权限 | 说明 |
| --- | --- | --- |
| 开发者 | **Write** | 能推分支、开 PR、合自己的 PR |
| `maintainers` / `product` team 成员 | **Write** | code owner 要能 approve，read 权限批不了 |
| 仅需查看 | Read | 看代码和 PR，不能推 |
| 仓库管理 | Admin | 限 1-2 人 |

**不要给普通开发者 Admin。** Admin 可以改分支保护，等于保护形同虚设。

### 组织设置里顺手关掉的

`组织 Settings → Member privileges`：

- Base permissions 设 **None**，权限通过 team 显式授予，避免新人自动获得所有仓库的访问
- 关掉 **Allow forking of private repositories** — 投研代码不该被复制到组织外
- 建议开 **Require two-factor authentication**（这是含需求基线和投研样例数据的私有仓库）

### 发给成员的话

邀请发出后，把这段贴给他们：

> 仓库：`https://github.com/your-org/ai-investment-copilot`
>
> 接受邀请后按 `docs/collaboration/远端接入手册.md` 第 9 节做环境。
>
> 三件事先知道：
> 1. 不要直接推 `main`，推不动的，都走 PR。
> 2. 绝大多数改动 **CI 绿了自己合，不用等任何人批准**。
> 3. 会被驳回的只有根 `README.md` 里那六条产品红线，其他都是建议。

## 9. 成员上手（每个人做一次）

```bash
git clone git@github.com:your-org/ai-investment-copilot.git
cd ai-investment-copilot

python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env

make hooks      # 提交时自动跑门禁，省掉「CI 红了再推一次」
make check      # 应在约 1 秒内全绿
```

`make check` 不需要数据库。要跑集成测试才需要，见 [`../../deploy/README.md`](../../deploy/README.md)。

### 第一个 PR

建议拿一个小的文档或测试改动走通流程，别拿功能代码练手：

```bash
git switch -c docs/readme-typo
# 改点东西
git commit -am "docs: 修正措辞"
git push -u origin HEAD
```

然后在 GitHub 上开 PR、等 CI 绿、自己合。**不用找人 approve。**

### 该读什么

| 优先级 | 文档 | 为什么 |
| --- | --- | --- |
| 必读 | 根 `README.md` 的产品边界表 | 六条硬约束，唯一会让改动被驳回的原因 |
| 必读 | [`CONTRIBUTING.md`](../../CONTRIBUTING.md) | 日常命令与流程 |
| 开工前 | 自己要动的模块的 `README.md` | 职责边界与验收要点 |
| 有空时 | [`../architecture/README.md`](../architecture/README.md) | 架构全貌 |

架构文档和分层规则值得读，但不必在写第一行代码前读完——违反分层的话 `make check` 会在 1 秒内告诉你，比读文档快。

## 10. 出问题时

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| `push` 报 `GH006: Protected branch update failed` | 想直接推 `main` | 这是设计如此。切分支走 PR |
| `push` 报 `rejected (fetch first)` | 建仓库时勾了 README，产生了无关历史 | 删掉远端仓库重建空库，别用 `--force` |
| PR 一直显示 Review required，但没人被请求 | `CODEOWNERS` 里 team 名写错或无效 | 打开 `.github/CODEOWNERS` 文件页看有没有黄色警告条 |
| Reviewers 出现了 team，但对方点不了 Approve | 该 team 只有 read 权限 | 改成 write |
| 自己的 PR 凑不出 approve | 该路径 owner 只有你一人，作者不能批自己 | team 里加第二个人 |
| 分支保护里搜不到 CI 的 check | 那个 job 还没运行过 | 先推一次让 CI 跑完，再回来配 |
| CI 里 `test` job 红但本地 `make check` 绿 | `make check` 不含集成测试 | 看 Actions 日志，通常是数据库或迁移问题 |
| 两个 PR 分别绿，合并后 `main` 红 | 没开 Require branches to be up to date | 补开这个选项 |
| 同时改了迁移的两个 PR，第二个报多个 head | alembic revision 链分叉 | 后合并者 `git rebase main` 后重新生成迁移 |
| hook 拦住了想提交的 WIP | 门禁没过 | `git commit --no-verify` 跳过，真正的防线是 CI |

### 把自己锁在外面了怎么办

只要没勾 **Do not allow bypassing the above settings**，仓库 Admin 可以随时进 `Settings → Branches` 改或临时停用规则。这也是建议不开那个选项的原因。

### 需要紧急合一个修复

正常流程也很快：开 PR、CI 约 1-2 分钟、自己合。如果碰的是四类受保护路径而 owner 不在线，让任意 Admin 临时在分支保护里给自己加 bypass，合完立刻撤回，并在 PR 里说明原因。
