# AI Investment Copilot 下一阶段产品开发计划

基线日期：2026-08-31

工作方式：在当前开发分支持续迭代；下一次团队成员分支合并形成大版本之前，不同步线上产品。

## 一、当前判断

第二阶段与 phase3 受控量化环境已经形成可用工程基线，但还不应把“三只证券能运行”解释为
量化有效性。当前最值得投入的不是继续扩大页面功能，而是把研究关系、原始证据、量化信号和
版本发布之间的边界做实。

近期发现的四项事实决定了后续优先级：

1. `copilot_dev` 有 1,147 条待确认关系，但存在明显的实体错配和低相关噪声，人工队列需要先
   去重、分级和硬门过滤。
2. 正式确认关系只有两只证券；第三只 A 股候选已经选定为比亚迪，但确认必须由专业研究员完成。
3. v3 行情截止到 2026-08-28，任何现在完成的人工确认都不能倒签，因此第三条信号必须进入新
   信号集并由确认日之后的新行情版本承接。
4. 业务库有 66 个文档 revision 引用没有对应的当前 MinIO 对象，数据库备份正确不等于完整
   可恢复，下一次大版本必须把数据库与对象存储作为同一发布单元。

## 二、P0：第三只 A 股人工确认闭环

目标：形成真实、可追溯、不可倒签的第三只 A 股信号，并完成三证券工程验收。

### 交付步骤

1. 冻结 `REL-ea2dd5a4df3547af` 及一手/二手来源快照，交由专业研究员独立复核。
2. 研究员必须核验 2026/2025 年 7 月产销快报，明确单月增长、累计下降、出口占比提升和未经
   审计限制，不得只抄二手研报结论。
3. 若结论为“修改”，先更新关系方向、强度与理由，再执行确认；若一手证据不足，保持待确认。
4. 在确认前重新归档两份公司公告，形成完整正文、内容哈希和页码/表格定位。
5. 以真实确认时间生成信号，冻结 `confirmed-relations-*-v2`，禁止回填 `generated_at`。
6. 构建覆盖确认日后至少 20 个交易日的新行情候选版本，再运行纯 A 股三证券市值中性验收。

### 验收条件

- 关系、证据、公告原件、研究员、复核时间和修改理由可双向追溯；
- 新信号生成时间不早于披露时间和人工确认时间；
- v3 和原信号集保持不可变；
- 三证券市值中性可以执行，但报告明确标记为工程烟雾测试，不宣称 Alpha；
- 同时开启行业中性时，如果行业单例导致信号归零，页面和结果必须给出明确诊断。

## 三、P0：证据与备份完整性修复

目标：下一次大版本发布前，任何“可恢复”声明都必须同时覆盖 PostgreSQL 和 MinIO。

### 工作项

- 向上传数据库的成员索取配套 MinIO 导出或 66 个原始对象；按 `object_key + version_id +
  content_sha256` 恢复，不修改数据库指针来迁就错误对象。
- 对仍可从公开来源重新获取的公告，走新 revision 重新归档；保留旧缺失记录和修复审计。
- 在备份产物中加入数据库对象引用覆盖率报告，并把恢复演练作为大版本发布硬门。
- 备份状态区分“数据库已捕获”“对象不完整”“完整恢复已通过”，禁止只输出笼统的完成信息。
- 清点并最终处置旧恢复演练匿名卷；在确认无保留价值前不删除。

### 验收条件

- 活动文档最新 revision 对象覆盖率 100%；
- 随机内容哈希抽检通过，候选比亚迪公告可从产品内直接打开并定位；
- 隔离恢复后数据库行数、对象版本、Alembic 版本和关键业务计数一致；
- 恢复演练结束后不遗留临时容器或匿名卷。

## 四、P1：候选关系质量与研究员工作台

目标：把 1,147 条待确认关系变成可处理、可解释、有优先级的研究队列。

### 产品能力

- 增加实体相关性硬门：新闻主体、证券主体和目标逻辑不一致时不得自动创建关系。
- 增加来源优先级：公司公告/监管披露优先于研报，研报优先于泛新闻；标题索引不得冒充正文。
- 对同一事实、同一假设的重复候选聚类，只展示主候选和差异来源，避免研究员重复确认。
- 提供“通过、修改、拒绝、暂不判断”批量工作台，并展示一手来源、二手解释、相反事实和
  数据缺口。
- 记录曝光、打开原文、修改方向、修改强度、驳回原因和处理耗时，形成队列 Precision@1、
  有效变化率和人工节省时间。

### 质量门禁

- 泛行业新闻错误关联到无关证券的比例必须为 0；
- 高优先级候选必须有可打开原文、披露时间和精确定位；
- AI 置信度不得代替人工结论，关系正式状态只能由逻辑负责人写入；
- 对已确认关系的任何修改都生成新审计记录，不静默覆盖历史。

## 五、P1：量化验证从“三只可运行”升级为“可解释样本”

目标：将当前工程能力与策略有效性评估严格分开。

- 三只证券只用于验证市值中性代码路径；正式研究至少扩展到 20—30 只具备同口径行情、点时
  市值和人工确认信号的 A 股。
- 信号集按确认时间滚动冻结，训练窗口和测试窗口按真正的 walk-forward 重新拟合，不使用固定
  全样本参数冒充滚动训练。
- 完成涨跌停三条供应端缺口处理、结构化公司行动、历史证券池/退市处理和交易费用敏感性。
- 对不同方向、强度、行业、来源类型做分层统计；样本不足时只报告覆盖率，不输出显著性结论。
- 保存“无市值中性、仅市值中性、仅行业中性、双中性”四组消融，解释单行业或行业单例对
  横截面结果的影响。

## 六、P1：集成与下一次大版本发布门禁

在团队下一轮分支合并前，当前分支只做本地开发、测试和评审材料准备，不更新线上镜像或数据。
下一次大版本候选必须一次性完成：

1. 合并团队搜索/知识问答、研究工作台及本分支的数据治理改动；
2. 解决冲突后运行 Python 全量测试、Ruff、mypy、前端检查与生产构建；
3. 形成数据库 + MinIO 成套迁移包，并通过隔离恢复演练；
4. 使用新行情候选和新信号集做灰度，不覆盖 v3 与两信号历史运行；
5. 配置正式域名与可信 HTTPS 证书，消除公网自签名证书告警；
6. 大版本验收通过后再发布线上，并保留一键回滚到当前 v3 的路径。

## 七、建议迭代顺序

### Iteration A：研究复核准备（当前）

- 完成比亚迪候选复核包、来源差异计算、填写校验和研究员回传说明；
- 不修改线上关系状态，不创建新信号集。

### Iteration B：证据闭环

- 收回研究员结论；归档一手 PDF；按结论修改或确认关系；
- 建立候选关系实体硬门和重复聚类的最小实现。

### Iteration C：新版本量化验收

- 冻结信号集 v2；生成覆盖实际确认日后的行情候选；
- 完成三证券市值中性工程验收和四组消融；累计至少 20 个交易日后再评估稳定性。

### Iteration D：团队大版本集成

- 合并成员分支；恢复 66 个对象；通过全量 CI 与恢复演练；
- 形成可登记、可灰度、可切换、可回滚的大版本候选，再决定线上发布时间。

## 八、明确不做

- 不为了凑够三只证券而确认中性、无关或证据不足的关系；
- 不倒签人工确认时间，不让 v3 承接确认日之后的新信号；
- 不在对象缺失时伪造原文或重写内容哈希；
- 不把三只证券工程测试宣传为策略有效或可交易结论；
- 不在下一次团队大版本合并前同步线上产品。
