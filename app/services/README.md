# app/services — Investment Thesis Engine

主要维护：逻辑引擎方向（问谁，不是评审权限）
PRD 层级：Investment Thesis Engine（PRD 8.2 核心层）

## 职责

核心对象、关系、状态机、版本、审计。这是产品的心脏，也是**人工确认闸门的唯一实现位置**。

建议的文件划分（按业务动作，不按对象 CRUD）：

| 文件 | 职责 |
| --- | --- |
| `thesis.py` | 卡片创建、编辑、发布、复制、关闭、检索 |
| `evidence.py` | 候选证据的确认 / 驳回 / 修改关联 / 暂不判断 |
| `status.py` | 汇总规则建议，处理人工接受 / 拒绝 / 修改 |
| `review.py` | 复核任务创建与处置 |
| `version.py` | 版本快照生成与差异计算 |
| `audit.py` | 审计留痕，被上述模块调用 |
| `permission.py` | 可见性过滤，被上述模块调用 |

## 人工闸门

PRD 5.4：AI 可以提取、拆解、建议，但确认最终表达、必要性、重要性和边界必须由人工完成。FR-S-002：系统按证据、阈值和复核日生成状态建议，**不自动发布正式状态**。

实现要求：

- 正式状态变更的函数签名必须包含 `actor` 和 `reason`，两者都不可为空。
- `app/calc` 的 `StatusSuggestion` 只能写入 `status_suggestion_log`，不能直接改 `thesis.status`。
- 人工处置结果（接受 / 拒绝 / 修改）单独留痕在同一条 log 上，包含 `acted_by`、`human_reason`。

任何绕过这条路径修改 `thesis.status` 的代码在评审时会被驳回。

## 版本规则（PRD 5.3）

| 情形 | 是否产生版本 |
| --- | --- |
| 草稿阶段连续保存 | 否 |
| 发布 | 是，V1 |
| 核心观点 / 关键假设 / 预期 / 失效条件 / 状态的正式修改 | 是 |
| 证据确认 | 写时间线；若导致关键字段变化，则同时产生新版本 |

**历史版本冻结当时可得信息，禁止使用未来信息覆盖历史记录。** `thesis_version.snapshot` 是全字段快照，生成后不允许 UPDATE。发现快照有误的正确做法是生成新版本并说明原因，不是改旧快照。

## 权限

PRD 12.1：

- 卡片支持私有 / 团队 / 授权范围（`Visibility` 枚举）。
- **证据可见性不得高于来源文档。** 写入证据时校验 `document.visibility_label`，不满足则拒绝。
- 管理员配置系统不等于拥有全部研究内容访问权。管理权限与内容权限分开判断。

权限过滤必须在这一层完成。`app/api` 不允许直连 `app/db`（`.importlinter` 强制），就是为了保证所有查询都经过这里的过滤。

## 审计（FR-A-003）

记录查看、创建、编辑、确认、导出和模型调用，可按对象追踪。

写审计与业务写入在同一事务里。审计失败则业务动作回滚——如果允许审计缺失，可追溯性就是空话。

## 状态机（PRD 5.2）

```
草稿 ──发布──► 验证中 ──┬──► 出现分歧 ──┐
                          ├──► 重大风险 ──┼──► 已关闭
                          └──────────────┘
```

"持续支持"不是状态，只作证据摘要展示。已关闭后不再生成状态建议，关闭时选择原因并生成复盘草稿（FR-S-004）。

状态流转的合法性判断在这一层，`app/calc` 只给建议不判合法性。

## 编排职责

这是唯一同时依赖 `app/ai`、`app/calc`、`app/ingest`、`app/db` 的模块。典型编排：

```
确认一条候选证据
  → permission 校验（证据可见性 ≤ 文档可见性）
  → db 写 evidence.confirmation_status = 已确认
  → calc.summarize_evidence 重算证据聚合
  → calc.check_invalidation 重算失效判定
  → calc.suggest_status 生成建议
  → db 写 status_suggestion_log
  → 若关键字段变化 → version 生成新快照
  → audit 留痕
  （全部在一个事务内）
```

模型与规则的结论冲突时不做自动仲裁，两边结论都呈现给研究员（ADR-0002 已接受这个代价）。

## 边界

- 不 import `app.api`、`app.workers`。被它们调用，不反向依赖。
- 不写 SQL。走 `app/db/repositories`。
- 不做数值计算。走 `app/calc`。
- 不直接调模型。走 `app/ai`。

## 测试

- `tests/unit/services/` 状态流转合法性、版本触发条件、权限判断，用假仓储。
- `tests/integration/services/` 完整编排与事务边界，需要数据库。

必须有的测试：

1. 状态建议不会自动改 `thesis.status`。
2. 缺 `reason` 的状态变更被拒绝。
3. 证据可见性高于来源文档时写入被拒绝。
4. 审计写入失败时业务动作回滚。
5. 版本快照生成后不可被修改。
